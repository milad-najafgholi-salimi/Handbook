**Logs** (or **logging**) are records of events that happen inside a system, application, or device. They are one of the most important tools for **debugging, monitoring, security, and understanding system behavior**.

---
## 1. What are logs?

A **log** is a **time-stamped message** generated by software or hardware that describes:

- What happened
    
- When it happened
    
- Where it happened
    
- Sometimes why it happened
    

Example log entry:
```
2026-02-02 10:14:32 ERROR Database connection failed (timeout)
```
This tells us:

- **Time**: 10:14:32
    
- **Severity**: ERROR
    
- **Event**: Database connection failure
    
- **Cause**: Timeout

---
## 2. Why logs are important

Logs help you answer questions like:

- Why did the system crash?
    
- What happened right before the failure?
    
- Is the system behaving normally?
    
- Is someone trying to break in?
    
- How often does a problem occur?
    

Without logs, debugging is mostly **guesswork**.

---
## 3. Common uses of logs

### 1. Debugging

Developers inspect logs to:

- Trace program execution
    
- Identify bugs
    
- Understand unexpected behavior
    

### 2. Monitoring

Operations teams use logs to:

- Detect system outages
    
- Track performance issues
    
- Monitor uptime
    

### 3. Security & auditing

Logs help:

- Detect unauthorized access
    
- Track user actions
    
- Investigate incidents
    

### 4. Compliance

Many industries **require logs** to be kept:

- Financial systems
    
- Healthcare
    
- Education platforms

---
## 4. Log levels (severity levels)

Most systems categorize logs by **importance**:

| Level            | Meaning           | Example             |
| ---------------- | ----------------- | ------------------- |
| TRACE            | Very detailed     | Function entry/exit |
| DEBUG            | Debug info        | Variable values     |
| INFO             | Normal operation  | Service started     |
| WARN             | Something unusual | Disk space low      |
| ERROR            | Operation failed  | File not found      |
| FATAL / CRITICAL | System crash      | Kernel panic        |
Not all systems use all levels, but the idea is the same.

---
## 5. Types of logs

### 1. Application logs

- Generated by applications
    
- Errors, user actions, workflows
    

Example:
```
INFO User login successful (user_id=42)
```
### 2. System logs

- Generated by the operating system
    
- Hardware, drivers, services
    

Examples:

- Linux: `/var/log/syslog`, `dmesg`
    
- Windows: Event Viewer
### 3. Security logs

- Login attempts
    
- Permission changes
    
- Firewall events
    

Example:
```
WARN Failed SSH login from 192.168.1.10
```
### 4. Access logs

- Who accessed what and when
    
- Very common in web servers
    

Example (web server):
```
GET /index.html 200 123ms
```
### 5. Audit logs

- Immutable records
    
- Used for compliance and legal reasons

---
## 6. Log formats

### Plain text

Simple, human-readable:
```
ERROR Failed to open file
```
### Structured logs (JSON)

Machine-friendly, easier to analyze:
```
{
  "timestamp": "2026-02-02T10:14:32Z",
  "level": "ERROR",
  "service": "auth",
  "message": "Invalid password"
}
```
Structured logs are preferred in modern systems.

---
## 7. Where logs are stored

- Local files
    
- System journals (e.g., `systemd-journald`)
    
- Centralized log servers
    
- Cloud logging platforms
    

**Centralized logging** is common in large systems so all logs can be searched in one place.

---
## 8. Log rotation (very important)

Logs can grow huge.

**Log rotation**:

- Splits logs by size or time
    
- Compresses old logs
    
- Deletes very old logs
    

Without rotation:

- Disk space can fill up
    
- Systems can crash

---
## 9. Logging best practices

### Do:

- Include timestamps
    
- Use appropriate log levels
    
- Log errors with context
    
- Keep logs readable
    

### Don’t:

- Log passwords or secrets
    
- Log too much in production
    
- Ignore log cleanup

---
## 10. Logs in embedded systems

In embedded systems:

- Storage is limited
    
- Logs may be:
    
    - Sent via serial (UART)
        
    - Stored in flash
        
    - Sent over network
        

Bootloader logs are often the **only clue** when a device fails to boot.

---
## 11. Logs vs Metrics vs Traces
| Concept | Purpose                 |
| ------- | ----------------------- |
| Logs    | What happened           |
| Metrics | How much / how often    |
| Traces  | End-to-end request flow |

---
## 12. Simple analogy

Logs are like a **black box recorder**:

- They record events
    
- You analyze them _after_ something goes wrong
    
- The better the logs, the easier the investigation
